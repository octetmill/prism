# URLTest regex-mode "Tag pattern" is POSIX ERE, evaluated by `grep -E`, not Lua-pattern and not plain-substring

The field was labelled "Regex (match by tag)" and shipped with a regex-looking placeholder (`.*HK.*\|.*JP.*`) since it was introduced, but `build-config`'s `match_any` evaluated it as `tag:find(part, 1, true)` — i.e. plain substring with `\|` as the only separator. The original code comment justified the choice on the grounds that "user values like `EU-France` contain literal hyphens, which Lua treats as a pattern quantifier" — true for `string.find` patterns, but it left a UI/engine mismatch where regex syntax (`[0-9]{2}`, `^`, `$`, `.`, `\d`) silently fell through as literal characters and matched nothing. The reported symptom: a user typed `ASIA-Singapore-\d{2}`, watched it fail to match every `ASIA-Singapore-0N` node, and had no signal that the engine was looking for the literal nine-character string `\d{2}` inside each tag. Three options were considered: (a) rename to "Tag substring(s)" and keep the engine as-is — safe but downgrades the field below user expectation; (b) Lua patterns native — cheapest engine but breaks every stored pattern containing a hyphen, including the placeholder-suggested form, requiring a migration; (c) true regex via shell-out. Picked (c) — POSIX Extended Regular Expressions via `grep -E`. Reasoning: existing stored patterns are plain substrings (that's all the engine ever did), and every literal substring is also a valid ERE — `EU-France` matches `EU-France-01` as ERE the same way it matched as substring (`-` is literal outside character classes; the only ERE metachar that shifts meaning between "plain string" and "ERE" in realistic tag values is `.`, which keeps matching the original character plus any other — a strictly-broader match, no existing user value silently loses members). `\|` is native ERE alternation, so multi-alternative patterns continue to work without change. The cost — one `grep -E` subprocess per regex-mode group — runs at config-build time (once on save / reload), not per request; on a router that's negligible. Lua 5.1 has no PCRE library in the OpenWrt base image, so a shell-out beat shipping a regex C module. Implementation in `build-config` step 3: a `regex_match_set(pattern, tags)` helper single-quotes the pattern and each candidate tag into one `printf '%s\n' 'tag1' 'tag2' ... \| grep -E -- 'pattern'` command, reads matching tags off `popen`'s stdout into a set, and the existing outbound-collection loop consults that set instead of calling `match_any` per-tag. Tags are filtered through the `urltest_regex_sources` allowlist *before* the grep call so a hostile source can't influence the regex engine with crafted strings (defensive, not load-bearing — grep is plain-text in/out). Single-quote escaping is the only shell escape needed (`'` → `'\''`), and UCI values are single-line so embedded newlines aren't a worry. PCRE-only metachars are explicitly *not* supported and are called out in the new help text on the `urltest_regex` form field: `\d` / `\w` / `\s` aren't ERE, write `[0-9]` / `[A-Za-z0-9_]` / `[[:space:]]` instead. Placeholder updated from `.*HK.*\|.*JP.*` (which was misleading even under the old substring engine — `.*HK.*` as a literal substring matches no real tag) to `ASIA-Singapore-[0-9]{2}\|EU-.*`, demonstrating both a bracket-class form and an alternation form. The `_outbound_regex` UCI field name is kept (`urltest_regex` in UI, `_outbound_regex` internally between step 2 and step 3); renaming would force a migration for zero readability gain. SEC-3 audit logging (per-source admit counts to stderr) is unchanged — the engine swap doesn't change what gets admitted, only which patterns successfully match.
