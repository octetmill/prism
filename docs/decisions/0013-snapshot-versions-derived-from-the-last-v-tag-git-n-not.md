# Snapshot versions derived from the last `v*` tag (`_git<N>`), not from a forward-looking `PKG_VERSION` in the Makefile

The original scheme (decision: *CI: tag-driven releases; rolling snapshot pre-release; `PKG_VERSION` = next planned release*) used `<PKG_VERSION>_pre<N>-r<R>` where `PKG_VERSION` was the *next* release being worked toward and `N` was commits since the last `v*` tag. Conceptually clean — `_pre` semantically reads as "leading up to the next release" — but it required `PKG_VERSION` to be a correct *prediction*. When a planned `0.6.0` got pre-empted by a `0.5.1` hotfix, the dance was: edit Makefile `0.6.0 → 0.5.1`, tag and push `v0.5.1`, edit Makefile `0.5.1 → 0.6.0`. Two of those three edits were strictly unnecessary — `release.yml` reads the version from the tag (`PRISM_VERSION` env, set from `${GITHUB_REF_NAME}`) and passes it to `package.sh`, which prefers it over the Makefile (`package.sh` `if [ -n "${PRISM_VERSION:-}" ]; then PKG_VERSION="$PRISM_VERSION"`). But the third edit (resetting `PKG_VERSION` back to the next planned after the hotfix) was real: without it, post-`v0.5.1` snapshots would have been `0.5.1_pre<N>` (= "pre-release leading up to 0.5.1"), implying the snapshots were *older* than the release they were actually built after — wrong direction in APK ordering. The root issue was that `PKG_VERSION` was a guess that the Makefile had to keep in sync with the release timeline. Switched the snapshot path to derive everything from the most recent `v*` tag: `<last-tag>_git<N>-r<PKG_RELEASE>` where N = commits since that tag (`git rev-list --count "${LAST_TAG}..HEAD"`). Snapshots now describe what they actually are — "N commits past v0.5.1" — and the Makefile needs no editing across a release. `_git<N>` chosen over `_p<N>` because Alpine's aports convention reserves `_p` for "upstream patch level" (e.g. `openssh-9.6_p1` mirrors upstream's tarball name) while `_git` is the conventional suffix for downstream VCS snapshots taken after a release — the latter is what these are. APK suffix ordering (alphabetical with `_alpha < _beta < _pre < _rc < (none) < _cvs < _svn < _git < _hg < _p`) puts `<tag>` < `<tag>_git<N>` < `<next-tag>`, so `apk upgrade` still picks newer snapshots and won't downgrade past a tagged release. **Bootstrap fallback retained:** if no `v*` tag exists in the repository, `package.sh` falls back to the old `<PKG_VERSION>_pre<N>` shape so the very first run (before `v0.1.0` exists) still produces a valid sortable version. **N=0 special case:** when HEAD sits exactly on the tag (local build at the tag, no `PRISM_VERSION` set), the suffix is dropped — the local build version matches the tagged release version exactly. **PKG_VERSION's surviving role:** it's still consulted by the OpenWrt SDK build path (which calls `BuildPackage` and reads it verbatim) and by the bootstrap fallback above; the standalone `package.sh` builder ignores it once any `v*` tag exists. Keep it set to a sensible value (typically the next planned release) for SDK-build label correctness, but releases no longer depend on it. Release procedure shrinks from two steps (tag + push, then Makefile bump) to one (tag + push). `CLAUDE.md` Packaging section and `CONTRIBUTING.md` Versioning/Releasing sections rewritten to match; `snapshot.yml` header comment updated.
