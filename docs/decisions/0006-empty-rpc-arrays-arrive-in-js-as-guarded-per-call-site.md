# Empty RPC arrays arrive in JS as `{}`, guarded per call site with `Array.isArray`; `/etc/prism/extra.json` ships a `{}` default

Two fresh-install bugs from one tester report (0.7.1 IPK on 24.10). **(1)** luci.jsonc — and the pure-Lua fallback — cannot distinguish an empty Lua array from an empty object (both are `{}` in Lua), so an RPC reply field built as `local out = {}` with zero appends serialises as the JSON *object* `{}`. The JS idiom `x \|\| []` keeps a truthy `{}` and the subsequent `.forEach` throws, killing the whole tab — the Basic-mode Status tab crashed with "(outbounds \|\| []).forEach is not a function" on any install with zero nodes, which is precisely the new-user first-run state and why it survived testing. The fix is the `Array.isArray(x) ? x : []` coercion already used by nodes.js/routing.js (added 2026-05-27 for the same root cause); this sweep closed the three remaining weak sites (status.js render, basic.js load, nodes.js \_showNodes) — every RPC array field crossing the Lua→JS boundary is now guarded. A shared `asArray()` helper and an `rpc.declare` `expect`-coercion were considered and rejected: `expect` only fills *missing* fields, it does not retype a present `{}`; and the per-site guard keeps the explanatory comment next to the hazard. The *deep* fix — post-processing known list keys to `[]` in `json_stringify_reply` — is deliberately deferred: it touches every RPC reply and per working practice needs on-router verification, not bundling into a shipping hotfix. Until then, any new JS consumer of an RPC array field MUST use the `Array.isArray` guard. **(2)** The Makefile declared `/etc/prism/extra.json` as a conffile (2026-05-19 layout decision) but no package ever shipped the file, so opkg's `resolve_conffiles` logged `file_sha256sum_alloc: Failed to open file` on every install where the user had never saved overrides. Fix: ship a `{}` default (a true no-op — `apply_extra`'s `pairs()` over the parsed empty object iterates zero times, and the md5 config-change comparison in the init script is unaffected). Verified against opkg-lede source (resolve_conffiles / backup_modified_conffiles / conffile_has_been_modified) that the upgrade path cannot clobber user overrides: 0.7.1 recorded **no** checksum for the missing conffile, `conffile_has_been_modified` returns 1 ("modified") for a NULL recorded value, so a user-saved extra.json is backed up before unpack and restored over the shipped `{}`, which lands at `extra.json-opkg` — the standard modified-conffile outcome. A postinst touch-if-absent was rejected: `resolve_conffiles` runs *before* the configure stage, so it would not fix the checksum error on first install. The staged default is `chmod 600` in package.sh to match `write_secure`'s mode on user-saved content (it may carry credentials); rpcd and build-config run as root, so nothing needs wider access.
