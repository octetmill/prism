# Clash YAML parser decodes double-quoted scalar escapes (`\U0001F1ED`-style flag emoji, `\"`, `\\`, `\uXXXX`, `\xXX`, `\n`/`\t`/…) instead of passing them through literally

Follow-up to the zero-indent `proxies:` fix below. Node names quoted with YAML's 32-bit `\UXXXXXXXX` escape (the form emitted for flag-emoji country prefixes, e.g. `"\U0001F1ED\U0001F1F0 香港 01"`) were showing up verbatim as literal backslash-digit text in the UI — the hand-rolled parser never interpreted double-quoted escapes at all, it just sliced between the two quote characters. Two call paths needed fixing since only one of them went through the char-walking `clash_read_quoted` (used for inline-flow values and array items): block-style `key: value` lines capture the whole value in one regex shot and previously stripped surrounding quotes with a bare pattern match, no escape handling. Both now funnel double-quoted content through a new `decode_dq_escapes`, which walks the (quote-stripped) string once, decoding `\xXX`/`\uXXXX`/`\UXXXXXXXX` via a small UTF-8 encoder (Lua 5.1 has no `utf8` library, and flag-emoji code points are non-BMP, so need the 4-byte case) and single-character escapes (`\n`, `\t`, `\"`, `\\`, …) via a lookup table. `clash_read_quoted`'s scan loop was widened just enough to stop treating an escaped character as the string terminator (copy `\` + the next char verbatim while hunting for the real closing quote; the hex digits of `\x`/`\u`/`\U` can never collide with a quote or backslash, so no separate length bookkeeping is needed during the scan — `decode_dq_escapes` does the actual interpretation once the true end is found). Deliberately did NOT touch nested block-style list items (`alpn:` / `- h2`) — those are re-parsed by `clash_parse_list` → `clash_read_value` → `clash_read_quoted` regardless, so they already benefit without a separate code path. Verified against the same real-world 36-node subscription (all flag emoji now render correctly) plus synthetic fixtures for `\"`, `\\`, doubled `''` single-quote escapes, and inline-flow `\U` escapes — all decode correctly. One synthetic case (a `\t` escape inside a name) was deliberately included to confirm it does NOT bypass the pre-existing tag safety filter: decoding produces a literal control character, which `ob.tag:find("[%c]")` still correctly rejects, exactly as it would for a literal control character pasted into a name — the escape decoder does not weaken that guard.
