# Post-add latency test: a subscription's FIRST successful import forks a runner pass scoped to its new tags

"Test after a subscription is added" is detected in `sync_one`, not in the UI: "added" only becomes meaningful when the first sync actually lands nodes, and the reliable signal for that is *no nodes file existed before this sync's `write_nodes_file`* (`lib.file_exists` checked just before the write). That definition deliberately covers a sub whose first sync attempt failed (the later successful one still counts as first import) and a deleted-and-re-added sub (new uid ⇒ no file), while plain re-syncs never trigger — node drift is the periodic auto-test's job, and testing on every manual sync would be noise. The trigger fires after the UCI status commit, gated on `clash_api_enabled` AND `test_runner_busy()` being false: the runner's lock drops concurrent forks rather than queueing them, so forking while busy would not only lose the run but leave a freshly-written `.test-all-tags` behind to silently scope someone else's next full pass — the same reason `test_all_start` pre-checks busy before writing the tag file. That shared logic is now factored into `test_runner_busy()` / `fork_test_runner(tags)` (used by both `test_all_start` and the sync hook; `test_all_start` shrank to gate + fork). UI side: the backend-forked run starts during the sync RPC and outlives the tab reload the UI performs after a sync, so `nodes.js` gains `_resumeTestPoll()` — on render it checks `test_all_status` and, when a runner is in flight, adopts it with the standard `_pollTestAll` loop (detached span instead of a banner element; `_pollTestAll` already guards on `parentNode`/null). The same resume path also re-attaches a Test-all the user started before switching tabs, which was previously lost-to-view. Verified in the stubbed harness: first sync → file + scoped fork + syslog line; re-sync → no trigger; first sync under a busy runner → no fork and no tag file.
