# Manual-node tag renames propagate to routing references; tag stays the identity key

A user renamed a manual node and every rule pointing at it silently fell back to `direct` (build-config's validate_tag keeps the config loadable but reroutes the rule). Considered referencing manual nodes by their section uid instead — rejected: subscription nodes have no UCI section, so the tag is the only identifier that exists for *every* outbound (and it is what sing-box keys on), and a dropdown storing uids for manual nodes but tags for subscription nodes would put two value kinds in one option. Fix: `nodes.js` hooks the tag option's `write` and rewrites `rule.outbound`, `routing.final_outbound`, every urltest `urltest_outbounds` member list and `basic.server` from the old tag to the new one with plain `uci.set` calls — same staged change set as the rename, so Save & Apply commits both atomically and Reset reverts both together. Propagation is deliberately SKIPPED when the old tag is not unique among outbounds: with a duplicate tag the references still resolve after the rename (first-seen-wins dedupe makes the duplicate the new resolution target), so rewriting them would steal the duplicate's references. Only exact-element matches in list options are rewritten — tags legitimately contain spaces, so no split-on-whitespace handling anywhere in this path. Upstream subscription tag renames remain unfixable by design; regex-mode groups are the tool for fleets whose tags churn.
