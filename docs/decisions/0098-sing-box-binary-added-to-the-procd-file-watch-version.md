# sing-box binary added to the procd `file` watch; version cache cleared on every service (re)start

User report: after upgrading the sing-box package on the router, the Overview footer kept showing the old version. Two independent causes, both fixed in `root/etc/init.d/prism`. (1) **Stale display.** `luci.prism`'s `singbox_version()` caches the first line of `sing-box version` in `/var/etc/prism/.singbox-version` (tmpfs) so the 5s Overview poll and every subscription sync don't fork the ~10MB Go binary. Nothing ever invalidated that cache except a reboot wiping tmpfs — so an in-place `apk add` / `opkg install` left the footer on the pre-upgrade string indefinitely. Fix: `rm -f /var/etc/prism/.singbox-version` near the top of `start_service`, before the `enabled` gate, so any Save & Apply / UCI commit / WAN-up / manual restart / disabled→enabled flip forces a re-detect on the next read. Cost is one `sing-box version` fork on that next read; the steady-state poll path is untouched. Chose this over a per-read mtime check (binary newer than cache file) — that would have caught a bare `apk add` within one poll with no trigger, but adds a `stat`/fork to the hot path, and the deeper problem (2) needs a service restart anyway. (2) **Stale running process.** `procd_set_param command "$SINGBOX" run -c "$1"` stores the *path*, so any genuine restart of the `singbox` instance already re-execs whatever is on disk — but after a package upgrade nothing triggers one: a `reload` re-runs `start_service`, procd diffs the instance definition, sees `command` + config-file hash unchanged, and leaves the old process running. Fix: add `"$SINGBOX"` to `procd_set_param file` alongside the generated config, mirroring the exact `file`-hash trick already used for `active-watch` (decision context: procd re-checks watched-file hashes only when `start_service` re-enters, not via inotify). After an upgrade the binary's hash no longer matches, so the next `start_service` run restarts the instance onto the new binary. Residual gaps, accepted: a bare `apk add` with no follow-up trigger leaves both process and footer on the old version until the next `start_service` (consistent, self-heals); a crash→procd-respawn re-execs the new binary without running the init script, so the footer lags until the next `start_service` or reboot. Immediate on-router fix for an already-stuck install: `/etc/init.d/prism restart && rm -f /var/etc/prism/.singbox-version`.
