# `build_route` emits an unconditional `ip_is_private=true → direct` rule so LAN/loopback/link-local/ULA destinations bypass the proxy without requiring a user routing rule

In tproxy / tproxy_mixed mode `firewall.sh` already filters RFC1918, link-local, multicast, CGNAT and friends at the nftables prerouting stage (the `V4_RESERVED` / `V6_RESERVED` sets), so a `final_outbound` set to a proxy server still leaves LAN-to-LAN traffic on the local network. In **tun** mode there is no such firewall hook — TUN captures every IP packet — so a user who picked TUN + a proxy as their Default server would silently tunnel LAN traffic (router admin, file shares, printers) into the proxy and break LAN access; the previous `build-config` emitted nothing for the private-IP case. The fix is a single route rule injected in `build_route` after the DNS-hijack pair and before any user-defined rule: `{ ip_is_private = true, outbound = "direct" }`. The matcher (`route/rule/rule_item_ip_is_private.go`, `sing/common/network/addr.go:IsPublicAddr`) matches RFC1918 + loopback + multicast + link-local + ULA + unspecified, and intentionally *does not* match CGNAT (100.64/10) or the IPv4 fakeip default (198.18/15). Verified available since sing-box 1.11 (`option/rule.go` at v1.11.0 and v1.12.0), so it works on Prism's whole 1.12+ floor. **Fakeip safety**: sing-box demaps fakeip → FQDN at the *start* of `matchRule` (`route/route.go:434-448`), before the rule-evaluation loop; after demap `metadata.Destination.Addr.IsValid()` is false and `IPIsPrivateItem.Match` (rule_item_ip_is_private.go:30) returns false. So even with IPv6 fakeip on (whose default range `fc00::/18` sits inside ULA `fc00::/7`) fakeip routing keeps working. In tproxy mode the rule is inert and harmless. A user who needs to proxy a private destination (rare — e.g. routing to a private IP at the far end of an existing VPN) can place their rule above it; left unconditional rather than behind a UCI toggle because a toggle would add a setting nobody should need to touch.
