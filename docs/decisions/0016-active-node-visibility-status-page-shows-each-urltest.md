# Active-node visibility: Status page shows each urltest/selector's current member, and a background daemon logs every flip

Builds on the clash API plumbing decision #1: with sing-box's `/proxies` endpoint already available on loopback, the user's question "how often is `auto` actually flipping members, and is my `tolerance` too tight?" had no answer in the UI — the Status page's `via <group>` line was a static UCI read that never reflected the live selection. Two pieces. (1) **`/usr/libexec/prism/active-watch`** — a Lua daemon that GETs `/proxies` every 10 s, diffs each urltest/selector group's `now` against a tmpfs snapshot at `/var/etc/prism/.active-nodes.json`, and writes one `daemon.info` syslog line per change: `group 'auto': active node HK-01 -> HK-03 (142ms)` (the latency is from the new member's `history`, not the group's). Internal helpers whose tag starts with `_` (notably `_prism_test_all`) are filtered out — they're machinery, not user-configured groups, and would otherwise spam the log. The daemon is a second procd instance declared by `/etc/init.d/prism` alongside sing-box, gated on `prism.global.clash_api_enabled=1` — when the flag flips off, the reload re-enters `start_service`, `prism_declare_active_watch` no-ops, and procd's instance reconciliation tears the daemon down. The active-watch instance's `procd_set_param file` points at the daemon script itself, so a package upgrade that rewrites the script triggers a procd-driven restart on the next reload (without this, the old Lua interpreter stayed alive indefinitely and quietly ran pre-upgrade behaviour — observed once during this work). Snapshot lives on tmpfs so a reboot primes it cleanly: the first successful tick after boot stashes the current state without emitting any "changed" line. Polling at 10 s is ~6× oversampling for the typical 60 s urltest interval — fast enough to catch every flip, idle cost is a single loopback HTTP round trip plus a ~20 KB JSON parse, well under the router's noise floor. The daemon never traps signals: SIGTERM from procd interrupts `os.execute("sleep …")` and the Lua process exits at its default disposition, which is enough — no in-flight write to leak since the snapshot is renamed atomically. (2) **Status page Groups panel** — a `table.cbi-section-table` between the runtime row and the log boxes, one row per group: `tag → now  <latency-badge>  <type · interval · ±tolerance>`. The latency badge reuses the same colour bands as the Nodes panel (`label-success` <300 ms, `label-warning` <800 ms, `label-danger` ≥800 ms) but the function is copy-pasted rather than extracted into a shared module — one helper isn't worth a new require for a single consumer. UI tuning metadata (interval / tolerance / selector default) is joined in by the RPC from UCI, not pulled from the clash response — the API doesn't surface those fields, and putting them next to the live `now` is the whole point: the user sees `auto → HK-03 (142ms)  urltest · 1m0s · ±50ms` and has the tuning right next to the evidence of churn. The panel hides entirely when the snapshot is empty or clash API is off, so a feature-flagged-off install collapses back to the original layout with no dangling "Groups: —" placeholder. (3) **`get_active_groups` RPC** — reads the daemon's snapshot rather than fetching `/proxies` itself, so the 2 s UI poll stays cheap (one file read, no HTTP) and the UI sees the same view the daemon is logging against — a flip in the log and a flip in the panel are guaranteed to refer to the same observation. ACL adds it to the `read` list. Returns `{error: "clash API disabled"}` when the feature flag is off, matching the `test_node` convention. The deferred *active-member dropdown on Status* from decision #1 is intentionally still deferred: this entry adds read-only visibility, not a write path. (4) **Restart-event annotation** — the daemon's log distinguishes three "current selection" contexts so a syslog grep can tell them apart: `starting` (cold prime, first successful poll), `after sing-box restart` (procd-reported pid changed since last tick — uses ubus `service list` to read `instances.singbox.pid`), and `resuming` (fetch streak recovered after >=1 missed poll, sing-box pid unchanged — the network had a hiccup, not a restart). A failure-streak heartbeat fires one `warning` line at ~60 s of consecutive fetch failures and one `info` recovery line when the streak breaks, so silent staleness can't be mistaken for "everything is calm". Group lifecycle is logged too: `now tracked` on appearance, `no longer present` on removal — the user troubleshooting "why did my auto group stop working" finds the deletion event in the same log they use for flips. (5) **Singbox procd instance must be named** — the prism service originally ran sing-box as procd's auto-named first instance; with `active_watch` added, the substring grep for `"running":true` in `service_running()` (rpcd handler) and the watchdog cron now matched *either* instance, so a dead sing-box plus an alive watcher read as healthy. **This is the LAN-blackhole bug** the watchdog exists to recover from, defeated by its own sibling instance. Fix: `prism_declare_instance` calls `procd_open_instance singbox`, and both callers walk the parsed JSON to `instances.singbox.running` specifically (`luci.jsonc` in Lua, `jshn` in the shell watchdog). Critically, **ubus's `instance` parameter on `service list` is accepted-but-ignored on at least some procd builds** (observed on a live OpenWrt 25.12 router during this work: asking for `instance:singbox` returned every instance), so the fix cannot rely on the filter to scope the reply — it must parse the full list and walk the path. Any future code that needs "is sing-box running?" must use the same pattern; falling back to grep, even with the instance filter set, will silently reintroduce the LAN-blackhole bug. Renaming the instance forces a one-time sing-box restart on upgrade as procd swaps the old auto-named instance for the new named one. The daemon also tracks sing-box's pid via `singbox_pid()` and treats a change between successful polls as the authoritative restart signal — required because a sub-10 s restart (the common case for a config Save & Apply) doesn't fail any 10 s poll and the fail-streak signal alone misses it.
