# Latency test runner must release its lock on every post-acquire exit path

Field report: hourly auto-test was firing (`logread` showed `auto-test: probing all nodes (every 1h)` every hour) yet every node's Latency cell stayed frozen at ~9h old. Root cause: `test-all-runner` serializes runs with OpenWrt's `lock -n /var/lock/prism-test-all.lock`, but that command holds the lock via a **backgrounded helper process that outlives the runner** — `ps` showed a live `lock -n …` process (pid 9978) long after its runner had exited. The runner's `bail()` path did `os.exit(1)` without `release_lock()` (only the clean success path released), and a *transient* failure — `probe sing-box instance failed to start` at 00:21, recorded in `.test-all-status` — took that path. The orphaned `lock` helper then held the lock indefinitely, so every subsequent hourly runner failed its own `lock -n` and silently `os.exit(0)`'d (the "probing all nodes" log line lives in `hourly`, printed *before* the fork, so it kept logging while nothing ran). The in-code comment claiming the lock "releases automatically when this process exits (any signal, including SIGKILL)" was simply wrong for OpenWrt `lock`. Fix: move `release_lock` above `bail` and call it on both leaking paths — `bail()` and the `total == 0` early `os.exit(0)`; the only `os.exit` that intentionally does *not* release is the `lock -n`-failed branch, which never held the lock. The non-acquire branch's comment now records that. `/var/lock` is tmpfs so a hard SIGKILL (no `lock -u`) self-heals on reboot; the in-process exit paths — the realistic leak vector — are now all covered. Immediate on-router unwedge for an already-stuck instance: `lock -u /var/lock/prism-test-all.lock` (or `kill` the orphaned `lock` pid).
