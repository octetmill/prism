# Latency-probe budget raised to 5000 ms / 8 s wall clock, and a failed probe now reports *why* it failed

Field report: a node marked `timeout` in the Nodes table worked perfectly when actually used. Reproduced on the router against an ephemeral `--probe` instance: `/proxies/<tag>/delay?timeout=3000` → HTTP 504 `{"message":"Timeout"}` at 3.001 s, the same tag at `timeout=10000` → `{"delay":2118}`. Measured idle, the four EU `anytls` nodes of that subscription sit at 1.6–1.8 s against 200–450 ms for the Asian/US ones — under the old 3000 ms ceiling alone, but not against the `CONCURRENCY`-way TLS-handshake contention of a real batch, so they flapped run to run. `PROBE_TIMEOUT_MS` 3000 → 5000 and `REQ_TIMEOUT_S` 5 → 8; the two must move together, since a fetch that expires before the clash API answers produces the same false timeout with no status to explain it. Measured cost on a 240-node run: 32 s → 38 s. Separately, `parse_result` labelled *every* empty response body `timeout` — uclient-fetch drops the body on any non-2xx, so a real 504, a 404 for a tag absent from the probe config, and a dead loopback API were indistinguishable. The batch script now captures each probe's stderr and exit code into one `e_<idx>` file and `fetch_error` maps them: rc 8 + `HTTP error 404` → `unknown node`, + 504 → `timeout`, + anything else → `HTTP <code>`; rc 4 with `timed out` → `timeout` (ours, not sing-box's); otherwise `probe failed`. The first full run with it turned two nodes that had always read `timeout` into `HTTP 503` — the clash API refusing to probe them at all, which is a config fault, not a slow hop.
