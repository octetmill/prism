# `+lua` and `+libuci-lua` declared explicitly in `LUCI_DEPENDS`

Real-world failure: a user uninstalled `passwall2` and prism stopped starting with `env: can't execute 'lua': No such file or directory`, then after installing `lua` with `config: uci binding not available`. apk's auto-removal of "now-unused" packages orphaned both because passwall2 was the only installed package keeping them pinned in apk's needed set. On OpenWrt 25.12 apk, neither `luci-base` nor `luci-lib-jsonc` pulls in `/usr/bin/lua` or `libuci-lua` transitively — `luci-lib-jsonc` only links against `liblua5.1.5` (the shared library, not the interpreter binary) and `libuci-lua` is an independent Lua binding package not depended on by luci-base. prism however needs the interpreter for `#!/usr/bin/env lua` on every helper (`build-config`, `fetch-catalog`, `luci.prism`) and the `uci` Lua module for `require "uci"` in `build-config`. Declaring both explicitly makes apk treat them as direct deps of `luci-app-prism`, so removing an unrelated package can never orphan them. Side note from the same incident: after `apk add lua libuci-lua` restored the bins, rpcd's in-memory object registry was still stale — `ubus call luci.prism get_status` returned "Not found" until `service rpcd restart` re-scanned `/usr/libexec/rpcd/`. rpcd does not re-scan when handlers' dependencies change at runtime, only at its own startup. No code change needed for that — the postinst already does `service rpcd reload` on install, and the dep declarations now prevent the orphan path in the first place.
