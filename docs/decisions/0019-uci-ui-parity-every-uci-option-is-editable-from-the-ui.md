# UCI ↔ UI parity: every UCI option is editable from the UI; every user-editable UI field persists to UCI

Two-way invariant. (1) **UCI → UI**: every option in `/etc/config/prism` must have a control in some tab — otherwise the only way to change it is SSH + `uci set`, which defeats the point of shipping a web UI. Surfaced by the first-install Start-button gap: `global.enabled` ships at `0` and the Status page only exposed Stop + Restart; the `restart` RPC at `root/usr/libexec/rpcd/luci.prism` runs `/etc/init.d/prism restart` but does **not** set `enabled=1`, and `start_service` early-returns when `enabled=0`, so a freshly-installed Prism could not be turned on from the browser at all. Fix lives in the same change as this entry — see *Status page gains a Start button when sing-box is stopped*. (2) **UI → UCI**: anything the user can change in the UI must round-trip to UCI (or to another tracked persistent store like `/etc/prism/extra.json` or `nodes/*.json`) — no in-memory-only toggles, no UI state that vanishes on reload. The right home for a setting is the UCI section that matches its scope (`global`, `inbounds`, `dns`, `routing`, …) and a `form.Map` row in the matching tab. Runtime-only controls (Stop/Start/Restart on Status) are exempt because they're actions, not settings — but if such an action mutates a UCI flag as a side effect (Stop sets `enabled=0`), the inverse action must also exist somewhere in the UI (a Start path that sets `enabled=1`). Exceptions go through this log with a rationale.
