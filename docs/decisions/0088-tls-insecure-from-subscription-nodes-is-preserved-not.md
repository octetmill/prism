# `tls.insecure` from subscription nodes is preserved, not stripped

The subscription sanitiser in `build-config` originally stripped `tls.insecure` from imported nodes (it wasn't in `SUB_TLS_KEYS`) on the theory that a hostile sub publisher could silently disable cert verification. Real-world consequence: a large class of providers — particularly Chinese-market ones — set `skip-cert-verify: true` per proxy because they use decoy/fronted SNIs (e.g. `down-30005.sz.gfp.tencent-cloud.com`, `*.oss-cn-shanghai.aliyuncs.com`) that the real backend's certificate doesn't cover. Prism's strict mode turned every such node into `tls: failed to verify certificate: x509: certificate is not valid for any names, but wanted to match …` and the entire sub was unusable, while Clash / Clash Meta / sing-box's own remote-config loader / every phone client honoured the flag and connected fine. Investigation case: a SSRDOG-style Clash YAML with 41 anytls nodes, all unreachable. The narrow attack the sanitiser was defending against (sub URL takeover → flipping insecure on nodes the user already trusted with credentials and routing) does not outweigh making Prism strictly less compatible than every other client. Decision: add `insecure` to `SUB_TLS_KEYS` so the publisher-declared per-node value flows through verbatim. The rest of the strip list (`detour`, `ssh.private_key_path`, transport overrides, unlisted top-level keys, anything not in each protocol's `SUB_TYPE_KEYS` whitelist) stays — those are still defended. `disable_sni` was considered for the same treatment but left stripped: legitimate providers don't need it (they set `sni` to the decoy and accept the cert mismatch via `insecure`), so its only practical use is a hostile publisher deliberately suppressing SNI to ease MITM.
