# Live traffic digest on Status: bytes/sec, connections, session totals, sing-box memory — all via clash `/connections` only

The Status page already pulled `/proxies` for the Groups panel; the gap was "is anything actually flowing?", which the running badge alone can't answer (a wedged tunnel often looks running). The clash API exposes three nominally-relevant endpoints — `/traffic`, `/memory`, `/connections` — but `/traffic` and `/memory` are documented as WebSocket-streaming in upstream clash and sing-box's HTTP-GET behaviour on them is not something we wanted to depend on without on-hardware verification. **`/connections` is a plain HTTP GET** that returns `{ downloadTotal, uploadTotal, memory, connections: [...] }` in a single response, so one fetch covers all four signals we wanted: totals (the response itself), throughput (diff the totals across ticks for bytes/sec), memory (`memory` field — defensively typed, hidden when absent so a future sing-box that drops the field doesn't render a "memory: 0 B" row), and open-connection count (`#connections`). We piggy-back on the existing `active-watch` daemon — same 10 s tick, same gating on `clash_api_enabled`, same atomic-rename snapshot pattern — writing a separate file `/var/etc/prism/.clash-stats.json`. The two snapshots are *kept separate* deliberately: `.active-nodes.json` is read by both daemon (for diff) and rpcd (for the Groups panel), while `.clash-stats.json` is write-only from the daemon's side, and merging them would force `get_active_groups` to load fields it doesn't need (and vice versa for `get_clash_stats`). **Rate semantics:** the daemon stores `prev_total_up/down/ts` across ticks and computes `bps = (new - prev) / dt`; on the first tick (no prev), on a `pid_changed` tick (sing-box restarted, counters reset to zero), or on any counter regression (defense against an unobserved restart), rate is zeroed for that tick and the baseline re-armed — so a restart produces one `0 B/s` tick rather than a spuriously negative reading or a giant spike. **Resolution trade-off:** the dashboard ticks every 2 s but the underlying data refreshes every 10 s, so users see the same throughput value for ~5 ticks in a row; acceptable for a "is it flowing?" indicator. Sub-second granularity would require a browser-side WebSocket to `/traffic`, which is the natural follow-up if anyone needs it. **UI:** a single horizontal row above the Groups panel — `↓ <rate>  ↑ <rate>  <N> connections  session: <total↓> ↓ / <total↑> ↑  [memory: <mem>]` — rendered as inline flex pieces, not a table (it's one reading at a moment, not a growing list). Each value span is id'd so `_updateClashStats` does an in-place `textContent` swap every 2 s without rebuilding the row (avoiding a layout flicker every poll). The whole section is hidden when (a) clash API is disabled — RPC returns `error: "clash API disabled"`, same convention as `get_active_groups` and `test_node`; or (b) sing-box isn't currently running — the snapshot file persists in tmpfs across a stop, so a frozen reading from a stopped service is worse than silence. Visibility coordination between `_updateStatus` (knows running state) and `_updateClashStats` (knows error state) goes through `self._running`, so each handler can hide-on-its-own-signal without contradicting the other. **What we deliberately did NOT include:** the per-connection list (the `connections: [...]` array) is parsed only for its length — never transmitted through rpcd to the browser. A busy router can have hundreds of connections × ~20 fields each; that's a memory-budget violation on a constrained device and a layout problem on a glance-first page. If we ever want a "top talkers" view it should be a separate on-demand modal with its own RPC, not bolted onto the Status poll. ACL adds `get_clash_stats` to the `read` list.
