# Periodic latency testing: one full runner pass per hourly tick (`auto_test_hours`), not a per-subscription-sync trigger

Builds on the ephemeral-probe-instance entry below; ships the "periodic auto-test timer" deferred since decision #19. The intuitive hook — fire a test after each subscription refresh — is the wrong shape, though not for the obvious reason: the runner's `/var/lock/prism-test-all.lock` means N near-simultaneous triggers can never spawn N probe instances (a second runner exits immediately), but that same lock makes per-sync triggers *lossy* — the first synced sub starts a ~1-min run and every trigger from subs synced during it is silently dropped, so exactly the freshly-imported nodes the trigger was meant to cover go untested. Instead `hourly` runs ONE full pass after the entire `sync-subscriptions` walk (and its `reload_if_changed`) completes; the runner rebuilds the probe config from disk at start, so a single run covers every subscription's fresh nodes. Gating: UCI `prism.global.auto_test_hours` (hours, 0/unset = off, same convention as subscription `auto_update`), AND `clash_api_enabled` — the probe instance itself doesn't need the live API, but the gate keeps one master switch for the whole latency feature. Last-run bookkeeping is a tmpfs marker (`/var/etc/prism/.last-auto-test`) written *before* the fork: if the runner declines the lock (manual test in flight), the tick is skipped until the next interval rather than re-armed hourly against a busy lock. The marker dying with a reboot is by design — the first tick after boot re-primes `latency.json`, which the reboot wiped anyway (tmpfs). The hourly script also `rm -f`s `.test-all-tags` before forking so a stale scoping file from an aborted UI-triggered run can't narrow the periodic pass. Minimum effective interval is 1 h (the tick's own cadence); intervals are approximate by up to one tick, same as subscription auto-update.
