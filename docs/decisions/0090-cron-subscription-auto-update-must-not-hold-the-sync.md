# Cron subscription auto-update must NOT hold the sync lock across its RPC call

Regression hunt: the hourly auto-update logged `sync: auto-update, syncing subscription '<id>'` but never fetched — `last_sync`/`status`/`node_count` stayed frozen on the user's last manual sync, while manual UI syncs worked fine. Root cause: decision-era commit bac895e added a non-blocking `/var/lock/prism-sync.lock` *inside* the `sync_subscription` RPC to serialize the UCI full-file-rewrite, intending to share the lock the cron `sync-subscriptions` wrapper "already holds". But the wrapper held that lock for the *entire pass* and then called the RPC per due subscription; the RPC's `lock -n`, running as a separate process while the wrapper still held the file, failed every time, so the handler returned `status="busy"` and `sync_one` never ran. Two processes, one non-blocking lock, stacked acquire = guaranteed skip. Fix: make the RPC the single lock owner and drop the lock from the cron wrapper entirely. Each `sync_one` still runs under the lock (acquired by the RPC), so the rewrite race is still covered; an overlapping next cron tick is harmless because the just-updated `last_sync` makes a synced subscription no longer due, and the per-call RPC lock serializes any genuine concurrency (cron vs manual click). Manual syncs were never affected because nothing else held the lock at click time. Lesson: a non-blocking lock shared between a wrapper and the RPC it invokes must be held by exactly one of them, not both.
