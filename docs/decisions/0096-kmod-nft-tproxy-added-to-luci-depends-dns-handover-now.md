# `kmod-nft-tproxy` added to `LUCI_DEPENDS`; DNS handover now gated on firewall success

Field report from a clean router reinstall: the log showed `firewall: failed to load nftables ruleset, tearing down` immediately followed by `dns: managed DNS drop-in installed … dnsmasq routed through sing-box` — a split state where dnsmasq forwards to sing-box (potentially resolving into fake-IP ranges) while the TPROXY ruleset that would make those addresses reachable never loaded. Confirmed on-hardware before touching anything, per the "don't decide before testing" rule: `nft -f /var/etc/prism/prism.nft` reported a generic `No such file or directory; did you mean table 'fw4' in family inet?` against the whole `table inet prism { … }` block (expected — `nft -f` loads the table as one atomic batch, so any single failing statement inside makes every statement in it report the same enclosing-object error), and `lsmod | grep -i tproxy` was empty. `modprobe nft_tproxy` then failed outright with "failed to find a module named nft_tproxy", and `apk info` on that router listed `kmod-nft-core`/`-fib`/`-nat`/`-offload` but no `kmod-nft-tproxy` — the kernel module providing the `tproxy` nft expression Prism's ruleset uses was simply never installed. `nftables-json` (decision above) only supplies the userspace `nft` binary; nothing in `LUCI_DEPENDS` previously pulled in the kmod, so a router without it from some other source (stock fw4 doesn't need TPROXY) silently gets a package install that can never actually apply its firewall rules. Fix: add `+kmod-nft-tproxy` to `LUCI_DEPENDS`. Independently, `root/etc/init.d/prism`'s `start_service` was discarding `firewall.sh start`'s exit code entirely (`[ -x "$FIREWALL" ] && "$FIREWALL" start`), so the DNS drop-in installed unconditionally even on a firewall failure — the direct cause of the split state observed, and not specific to this one missing-kmod case (any future `nft -f` failure would reproduce it). Fixed by capturing the exit status into `firewall_ok` and only calling `install_dns_dropin` when it succeeded; a failure now falls through to `remove_dns_dropin` (dnsmasq keeps/reverts to its own resolvers) plus an explicit `dns: firewall setup failed, keeping dnsmasq on its own resolvers` log line, so the failure mode becomes "proxy doesn't work yet" rather than "clients get addresses nothing routes to".
