# `.ipk` outer container must be a gzip-compressed tar, not a GNU `ar` archive

A 24.10 user reported installing `luci-app-prism` from the opkg feed, getting `Configuring luci-app-prism.` with no error and the package listed by `opkg list-installed` — yet no menu entry, and `find /usr/share/luci -iname prism` returned nothing. First guess (stale LuCI menu index cache) was wrong: the files were not on disk at all, so there was nothing to cache. Pulled the actual released asset (sha256 matched the release; the feed `cp`s it verbatim) and confirmed its `data.tar.gz` *did* contain `./usr/share/luci/menu.d/luci-app-prism.json` and all 43 files and extracted cleanly with stock `tar`. The payload was fine. The differentiator: `package.sh` built the `.ipk` with `ar cr` (a Debian `.deb`-style GNU `ar` archive, member names written with trailing slashes — `data.tar.gz/`), whereas OpenWrt's own `ipkg-build` emits a **gzip-compressed tar** of `./debian-binary ./data.tar.gz ./control.tar.gz` by default — which is what every working package on the router (luci-app-momo, luci-app-firewall, …) is. On 24.10 opkg this difference is silent and fatal: opkg registers the package and runs its postinst but extracts zero files when the outer is `ar`. Fix: pack the three members with `tar --owner=0 --group=0 -czf` instead of `ar cr`; dropped the now-unused `ar`/binutils requirement. The APK path (25.12) is unaffected — `apk mkpkg` builds that container. Re-release as `v0.7.0-r2` (packaging-only) so the feed serves a working IPK.
